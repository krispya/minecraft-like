So far the camera has been configured once on the `Canvas` and never touched again. But a game camera *moves* — and in our architecture, things that move are entities driven by systems. In this chapter we turn the camera into an entity with `Position` and `Rotation` traits and render it with a `CameraRenderer`, setting the stage for the orbit controller in the next chapter.

## Why make the camera an entity?

Until now the camera has been a `Canvas` prop — configured once and forgotten. That works for a static viewpoint, but our camera will orbit the player, follow movement, and respond to input. In our architecture, anything that changes over time is world state that **systems** update and **renderers** draw. So the camera becomes an entity just like the player.

Two new traits:

```tsx
// traits.ts
export const Rotation = trait(() => new Quaternion());

export const Camera = trait();
```

`Rotation` is a quaternion (three.js's preferred rotation format — no gimbal lock), and `Camera` is another tag trait.

## The spawnCamera action

The camera spawns at a fixed position, rotated to look at a target point just above the player's feet. We compute the rotation with a `lookAt` matrix:

```tsx
// actions.ts
spawnCamera: ({ position = [15, 15, 15], target = [0, 2, 0] } = {}) => {
  const pos = new Vector3(position[0], position[1], position[2]);
  const matrix = new Matrix4().lookAt(
    pos,
    new Vector3(target[0], target[1], target[2]),
    new Vector3(0, 1, 0)
  );

  return world.spawn(
    Camera,
    Position(pos),
    Rotation(new Quaternion().setFromRotationMatrix(matrix))
  );
},
```

`Matrix4.lookAt(eye, target, up)` builds the orientation that points from `eye` toward `target`, and `setFromRotationMatrix` extracts it as a quaternion. This same eye/target/up math powers the orbit controller in the next chapter.

## The CameraRenderer

Same renderer pattern as the player and ground — query the world, draw with R3F:

```tsx
// view/camera-renderer.tsx
import { PerspectiveCamera } from '@react-three/drei';
import { Entity } from 'koota';
import { useQuery, useTrait } from 'koota/react';
import { Camera, Position, Rotation } from '../traits';

export function CameraRenderer() {
  const cameras = useQuery(Camera, Position, Rotation);
  return cameras.map((entity) => <CameraView key={entity.id()} entity={entity} />);
}

function CameraView({ entity }: { entity: Entity }) {
  const position = useTrait(entity, Position);
  const rotation = useTrait(entity, Rotation);

  return (
    <PerspectiveCamera makeDefault position={position?.toArray()} quaternion={rotation?.toArray()} />
  );
}
```

Drei's `PerspectiveCamera` with `makeDefault` replaces the `Canvas` default camera as the active one. Its position and orientation now come entirely from the entity's traits — whenever a system writes to `Position` or `Rotation`, `useTrait` re-renders the view and the camera moves.

## Wiring it up

Add `<CameraRenderer />` inside the `Canvas` and spawn the camera in `Startup`:

```tsx
function Startup() {
  const { spawnPlayer, spawnGround, spawnCamera } = useActions(actions);

  useEffect(() => {
    const player = spawnPlayer({ position: [0, 1.4, 0] });
    const ground = spawnGround();
    const camera = spawnCamera();

    return () => {
      player.destroy();
      ground.destroy();
      camera.destroy();
    };
  }, [spawnPlayer, spawnGround, spawnCamera]);

  return null;
}
```

Since the entity camera is now the default, we can drop the `position` from the `Canvas` `camera` prop:

```tsx
<Canvas shadows camera={{ fov: 45 }} style={{ position: 'absolute', inset: 0 }}>
```

Visually nothing dramatic changed — the camera is still fixed, looking at the player. But architecturally everything changed: the camera is now data in the world, which means systems can drive it. That's exactly what we do next with the orbit controller.
